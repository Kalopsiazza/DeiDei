# Teddy × ChatGPT × Codex｜协作流程

版本：1.0 · 生效于本次具名开发计划。Teddy 在 2026-09-11 明确委托。

## 职责

| 角色 | 负责 | 不代替谁 |
| --- | --- | --- |
| Teddy | 说明原玩法；决定产品取舍、画风与页面选择；转交线程；授权合入与发布 | 不需要独自查完代码问题 |
| ChatGPT 规划者 | 写详细 PRD；设计架构、数据表示、通信协议与页面信息；切分工作包；审阅真实代码与证据；出后续包 | 不让执行线程代写 PRD、选择整体技术方案或自行批准需求 |
| Codex 执行者 | 依工作包取证、实现、出图、实机运行、测试、记录结果、提交 PR | 不自行增加玩法、重写产品文件、切换架构或宣布全项目验收通过 |

Codex 可以说明某个设计无法实现、发现遗漏并给出证据；是否改变设计由 ChatGPT 回来处理，影响产品的事项再由 Teddy 决定。

## 从讨论到执行

讨论记录 → ChatGPT 详细 PRD → ChatGPT 架构设计 → 编号工作包 → Codex 执行与证据 → GitHub 结果 PR → ChatGPT 验收 → Teddy 产品确认／合入 → 后续包。

讨论记录是参考资料，禁止直接据此开始新游戏开发。Codex 不修改本计划的 PRD、架构、总进度和工作包原文；疑问写到本包结果中。

第一轮是明确编写了 PRD 和验证架构的前期工作：规则取证、独立技术实验、页面概念图。完整产品 PRD 中的未知招式结果尚未具备，不以“先做起来”为由补写玩法。任务 02 可写独立技术验证程序；任务 01 只可写不改变判定的取证脚本。两者都不能直接移入正式产品。

第一轮完成后，ChatGPT 使用证据和 Teddy 的答案撰写正式产品 PRD，再完成正式架构；之后才发正式实现包。实验设计和正式产品设计分别标注，不能把前者默认为全项目最终方案。

## 编号与文件名

例：`第一轮｜任务 01｜a｜游戏规则详细确认`，机器编号 `R01-T01-a`。

- R01：总计划第一轮。
- T01：这一轮中的主题任务，标题保持稳定。
- a：该主题第一次执行包；等答案、设计修改或其他包结果后，由 ChatGPT 发 b，再发 c。
- a/b/c 不表示线程编号或优先级。同一个包内的小修复继续原分支；新的输入版本、目标或依赖阶段，用下一个字母。

| 对象 | 命名 |
| --- | --- |
| 工作包 | `docs/tasks/R01/R01-T01-a.md` |
| 执行分支 | `work/r01-t01-a-rules` |
| 结果目录 | `docs/results/R01-T01-a/` |
| 实验代码（仅被授权时） | `experiments/r01-t01-a/` |
| 报告 | `docs/results/R01-T01-a/REPORT.md` |
| 证据索引 | `docs/results/R01-T01-a/manifest.json` |
| PR 标题 | `[R01-T01-a] 游戏规则详细确认｜提交验收` 或 `｜部分完成待条件` |
| 提交标题 | `[R01-T01-a] 说明本次变化` |
| ChatGPT 验收 | `docs/reviews/R01-T01-a.md` |

其他任务换成自己的编号与英文主题。以后轮次使用 R02、R03 等；不沿用前轮结果目录。

## 并行与基线

第一批工作快照：`plan/r01-v1`。每个包均读取其中相应 1.0 版材料，记录解析出的 SHA。结果 PR 指向 `docs/design-discussion-20260911`，不由 Codex 合入。计划快照保持不变。

每个线程独立 clone、fork 或 worktree；不要三个线程在同一工作目录反复切分支。读取最新 main 仅用于了解是否有新变化；本包工作起点仍是指定快照。上游变化影响本包时报告给 ChatGPT，不自行改基线。

三个线程只写自己的结果／实验目录，任务 02 额外允许一份具名实验 CI 文件。禁止复制其他线程未验收代码、随手改根目录依赖或删除测试。没有写权限时使用自己的 fork；未能创建 PR 也保留分支、提交 SHA 和错误，不宣称已上传。

## 状态与通过条件

`ISSUED` 可领取；`RUNNING` 已实际开始；`PARTIAL` 仅完成部分；`BLOCKED` 缺条件；`SUBMITTED` 已提交待验收；`CHANGES_REQUESTED` 待修改；`ACCEPTED` 已由 ChatGPT 验收；`MERGED` Teddy 授权合入。

Codex 在自己的 REPORT 中写执行状态，不改总进度板。只有 ChatGPT 根据实际记录更新总进度；不能因为等待若干天就自动视为完成。未拿到某平台、图片工具、原参考图或凭据时如实写 BLOCKED/PARTIAL，禁止伪造截图、猜测测试数字或把概念图标为实机。

每个包都有准确的允许路径、测试要求、停止条件与验收条件。缺条件时先完成相互独立的部分；不越过未获许可的内容。

## 结果证据与验收

每包交 REPORT、manifest、实际产物。manifest 至少记录 task_id、input_ref/input_sha、prd_version、architecture_version、tested_code_sha、OS/CPU/工具版本、执行命令、退出码、证据相对路径及 SHA-256、未运行事项、等待谁回答。图像模型记录实际使用的工具／模型名和提示词，未知项写 unknown。

运行结果对应一个确定代码 SHA；报告提交可以晚于被测代码。只有报告改字时注明；代码再改就重测受影响项目。安装包给出 SHA-256 和可获取位置，避免用“最新包”混淆不同版本。

GitHub 保存小型图像、脱敏日志和报告；安装包、大录屏用该结果 PR 对应 Actions artifact 或其他已获准位置，记录失效时间。不得把临时下载地址当永久证据。不要上传密钥、会话凭据、机器私人路径、聊天全文、虚拟环境或缓存。

ChatGPT 回来时：读取 PR 真实 diff 与代码 → 核对允许范围 → 检查测试和截图是否对应提交 → 必要时复跑可用测试 → 明确通过／部分通过／退回及理由 → 更新进度并发下一包。Linux 自动检查不替代 Windows/macOS 实机；生成效果图不替代运行截图。

Teddy 确认玩法或喜欢某张图，不自动证明程序正确；测试通过也不自动证明 Teddy 已批准设计。没有新的授权，不自动合入 main、发布版本、付费、购买证书或部署公网服务。
