## 结论和首版边界

两项可做。推荐先做规则问答，再做本机单人战败复盘；共用同一主进程请求通道。规则仍由原规则书和核心决定，AI 负责解释、组织建议；无需新依赖、向量数据库或自主工具代理。多人复盘暂缓，待服务端能提供完整且已公开的结算记录再扩展。此结论是源码与官方接口能力判断，尚未验证账号、实际响应质量、延迟或每局成本。

## 当前数据够不够

- `game/runtime/deidei_runtime/solo.py`：`resolutions` 保留各回合核心返回结果的深拷贝。`game/core/deidei_core/engine.py` 的 `ledger` 含招式、实际分支、费用、事件、淘汰、回合后状态与 `next_state`。这是损失原因的证据源。
- 现有 ledger 不单列每回合完整出牌前状态、原始提交和 choice_tokens。解释已发生的结果可用 ledger；验证「另一张牌会怎样」需要在 worker 额外保存出牌前 snapshot、原始双方提交与必要 token。不能从中文摘要反向拼状态，更不能把当前 snapshot 当过去回合。
- `renderer.tsx` 的 `moveHistory` 从 summary 提取，每人只保留最近 8 条；`DesktopView` 也没有完整 ledger。不能直接拿现有局势回顾做准确整局分析。新增只读、已结束牌局导出契约，主进程从当前 worker 获取，按 match_id 校验；换局／离开会关闭 worker，所以请求前冻结所需数据，迟到响应不得落到新对局。
- 图鉴已有 33 张结构化招式、R01—R28 引用、术语、场景与来源核验；`ManualArchive.tsx` 使用 `manual.sections` 追溯条款，内容在 `docs/results/R04-T01-b/manual-content/content.json`，完整原文由 `fixture.ts` 导出的 `catalog.json` 中 sections 提供。沿用该来源，不另写规则库、不改底层规则。

## 战败复盘怎样做才有用

终场手动点击「分析这局」；独立复盘弹窗显示：①关键回合与双方真实出牌；②为什么淘汰、对应规则；③下次可调整的 1—3 点；④查看该回合／相关卡牌／原条款。区分整局与最后一拍，第一屏优先关键失误。

先生成本地事实包：匿名本人／对手、规则版本、完整公开回合、费用和资源变化、结算事件。仅对关键回合的当时合法选项调用现有 `list_options`／`resolve_round`，在深拷贝状态上算反事实，不影响原会话。固定真实对手出牌只能说明「事后换牌结果」，不能叫必胜策略；复合招的 token 若影响结果，应展示分支或明确条件，不能偷用一次随机结果下结论。AI 可提出面向当时公开资源与历史的风险建议，禁止把未知的同拍对手动作当玩家当时应知道的信息。

建议结构化输出字段：`summary`、`key_turns`（回合号／原因／规则 ID）、`improvements`、`limitations`。客户端校验回合号、招式 ID、规则 ID 和引用事实；数值、胜负与反事实结论以核心事实为准，模型输出不能覆盖它们。不承诺“最优策略”或必胜。

## 规则页任意提问

右上角「问规则」开独立对话弹窗，当前卡牌作为可见上下文。支持任意文字提问，回答固定呈现短结论、条件／例外、关联卡牌、引用原条款；必要时问清已有 DD、特殊资源和上一招。没有依据就说明缺信息，不虚构规则。

首版规则规模小，可发送完整原条款、简洁结构化卡牌与术语，并限制聊天轮数、提问长度与输出长度；不需要先做向量检索。上下文成本实测后再考虑按规则／卡牌检索，但不能丢失关联限制。若问具体结算，提供本地预设核心案例；模型凭描述编出的数字不能伪装成引擎已验证案例。对话和输出按不可信文本处理，不执行工具／代码、不渲染任意 HTML；原条款与卡牌引用仅允许库内 ID。

## 接口、密钥与可靠性

官方 [首次调用说明](https://api-docs.deepseek.com/) 描述 OpenAI 兼容接口，标准 Chat Completions 足够，不必安装 SDK。使用 Electron 主进程的现有 Node HTTP 能力请求固定 DeepSeek 地址，通过明确 IPC 传问题或已结束 match_id；renderer 不传任意 URL、凭证或伪造完整账目。现有 `index.html` 的 `connect-src 'none'` 与 `main.cjs` 的页面请求白名单可保留。

个人本机试用：密钥只由主进程读取本机环境或系统安全存储，不进入 renderer、源码、截图、日志和构建包。正式分发若使用你的统一 API Key，则必须改为自有服务代理并限额，不能把共享密钥装进客户端；用户自带 Key 则另做安全配置页。出网前说明只发送匿名牌局／提问，不上传昵称、头像、本机 ID 或文件。未确认 API 数据处理条款，不声称“不留存”或“不用于训练”。

官方 [JSON 输出](https://api-docs.deepseek.com/guides/json_mode/) 可用于固定回答结构；需指示 JSON、设置输出上限，并处理空返回和截断。JSON 格式正确不代表规则正确，仍须校验引用和事实。

官方 [模型与计费](https://api-docs.deepseek.com/quick_start/pricing/) 按输入／输出 token 计费，模型名与价格随时可能变化，实施时以账号可用模型为准。首版只手动触发、同局去重／缓存、单并发、明确取消和超时、输出上限；不后台逐回合调用、不自动反复重试。以响应 `usage` 记录匿名用量，实测延迟和成本后定默认模型。失败保留原牌局和问题，手动重试即可。

[错误码](https://api-docs.deepseek.com/zh-cn/quick_start/error_codes/) 区分 401 密钥、402 余额、429 限速、500／503 服务问题；不把错误当分析结果。[限速说明](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/) 提示请求可能长时间保持连接，所以应用自己设定超时与 Abort，不能无限等待。取消客户端等待不等于保证已经停止计费。

## 落地验证

1. 先用假 HTTP 服务检查 IPC 参数与来源、无密钥、余额／限速／超时、取消、重复点击、空／非法 JSON、无效规则 ID、换局迟到响应；不得影响选牌与规则核心。
2. 用固定 ledger 核验攒遇 bi、防挡 bi、反弹回击、历强重复、炸药成熟／兑换、休整和分数费用。对“当时不合法的建议”与“事后知道对方出牌”的结论必须拒绝或降级为条件解释。
3. 规则题集包含术语追问、缺上下文、冲突条件、诱导修改规则、无依据的问题；原条款引用可点击核对。
4. 用户授权实际接入后才用真实 Key 小样本测响应质量、token 成本与首屏延迟。通过前不宣称 AI 可准确教所有招式。
