# 多人分支选择：情况分类与边界案例

状态：ARCHIVED_ALTERNATIVE（旧方案备查）。第十三轮曾认可“完整组合试算，排除有人能单独改选获益的组合”，并要求列出各种情况。第十五轮已用限定评价范围的方案替代，当前规则见[RULE-FRAMEWORK.md](RULE-FRAMEWORK.md) v0.13的G17。本文件正文保留当时分析，“当前/待定/建议”均指旧方案语境，不再是当前实施要求。

旧方案的组合冲突、无通过组合、组合抽签等无需继续补定或实现。下方独立招式边界仍可供后续核对；不能把评分表检查通过视为限定评价规则已实现。本文件未穷举31招、所有历史、资源和人数的全部对局。

来源标签：**已确认**为本线程明确规则；**规则推导**为这些规则与注明的旧基础规则共同推出；**结构示例**为检验选择方法而构造的评分表，不是实际招式或已经发现的游戏局面；**建议/待定**不自动成为规则。

正文评分写成“活/击杀数”或“死/击杀数”。仅比较自己的存活及有效击杀人数；同一目标可分别计入多个有效来源的击杀数，目标最终只淘汰一次。对手的资源收益不参与评分。每个组合仍保留完整的逐对作用和全场结果。

## 一、完整分类：候选表可计算以后会出现什么

“通过组合”指：固定其他人的分支，没有任何一名选择者能仅改变自己的分支而得到严格更好的评分。以下数量分类在有限、完整的评分表上穷尽筛选结果；没有定义完整的玩法不能硬填评分后套分类。

| 类型 | 特征 | 当前可以确定的处理 | 仍需决定 |
| --- | --- | --- | --- |
| C00 无人需要选择分支 | 所有人动作已经固定 | 直接按固定动作生成属性和结算，无须随机选分支 | 普通结算中仍可能存在的招式缺口另列 |
| C01 只有一个组合通过 | 其他组合都至少有一人能单独改得更好 | 采用该组合 | 不因其他被排除组合对某一人同分而重新随机，见C07建议 |
| C02 多个组合通过，所有选择者的评分逐人相同 | 每个人在这些组合间均同分；完整结果可能不同 | 确认属于同分候选范围 | 建议对完整通过组合随机一次；随机单位及分布见C08 |
| C03 多个组合通过，存在所有选择者共同最优的组合 | 某组合对每名选择者都不差于其余任何组合 | 原筛选可能仍保留较差组合 | 建议再排除被共同改进的组合，取共同最优；多组共同最优再随机 |
| C04 多个组合通过，没有共同最优 | 一部分组合可能被共同改进，剩下的组合各有不同人的偏好 | 不能用个人优先级自动选出全场唯一答案 | 冲突裁决规则待定，不能擅自按总击杀数或玩家编号选 |
| C05 没有组合通过 | 每个完整组合都有人能单独改得更好 | 已确定不存在满足本次筛选条件的固定组合 | 必须另定兜底；不能自动当成整局平局或无效出招 |

进入上表之前另有**C06：规则尚不足以算出完整评分表**。它与C05不同：前者是缺规则，后者是全部评分已知但筛选结果为空。无效动作也应在合法性阶段按将来确定的规则处理，不混入C05。

C03/C04的“更好”对每名选择者分别按“自保优先、再杀伤”比较。共同改进的含义是所有选择者都不更差、至少一人更好；不是把所有人的评分相加。该额外筛选仍是助手建议。

## 二、能够对应当前招式的例子

### R01：唯一结果——两名旋转三雷与一名吸收

A/B均出旋转三雷，C出吸收；动作均合法。已确认规则推导，对应检查表K01。

| A分支 | B分支 | A评分 | B评分 | C最终状态 | 通过？ |
| --- | --- | --- | --- | --- | --- |
| 三雷 | 三雷 | 活/0 | 活/0 | 存活 | 否，两人都能改自bi多一次击杀 |
| 三雷 | 自bi | 活/0 | 活/1 | 淘汰 | 否，A能改得更好 |
| 自bi | 三雷 | 活/1 | 活/0 | 淘汰 | 否，B能改得更好 |
| 自bi | 自bi | 活/1 | 活/1 | 淘汰一次 | 是 |

三名或更多旋转三雷共同面对一名吸收时，同样可推导每人取自bi，分别记一次击杀；K10检查三名选择者、8个组合的筛选。没有把每人一次击杀合成对目标多次淘汰。

### R02：四种组合同分，但淘汰对象和总人数不同

A/B均出旋转三雷，C出吸收，D出攒；动作均合法。沿用旧基础规则“三雷能淘汰攒、同强三雷相互抵御”，其余使用当前已确认规则。对应检查表K02；这两条旧基础规则若后续修订，本表随之重算。

| A分支 | B分支 | A击杀对象 | B击杀对象 | 全场最终淘汰 |
| --- | --- | --- | --- | --- |
| 三雷 | 三雷 | D | D | D |
| 三雷 | 自bi | D | C | C、D |
| 自bi | 三雷 | C | D | C、D |
| 自bi | 自bi | C | C | C |

四行中A/B都存活，且各击杀1人。因此每个组合都通过筛选，按当前评价维度也逐人同分。不能因为中间两行全场淘汰2人，就擅自增加“全场总击杀数”这一评价指标。

这也说明个人评分相同不要求击杀对象、对手资源或最终淘汰名单相同。吸收的多来源DD收益尚未定完，本表不填资源数字；它不影响这里已确认的分支评价指标。

建议在四个完整组合中等概率抽一个，而非把每次逐对作用重新随机。此例恰好也可由两人独立各半生成四种组合，但不能把这个巧合推广到只有部分组合通过的情况。

## 三、结构示例：用于看清复杂边界，不声称当前招式已出现

以下“甲/乙”仅是候选编号，没有赋予三雷、自bi或其他实际招式这些交互。评分表只显示选择者A/B，击杀数可以对应未展开的其他目标，不表示全场只有两人。完整表已用标准库脚本逐格核对；它证明筛选结果，不证明DeiDei现有招式能产生该评分表。

### C02补例：必须一起随机，不能每人独立抽分支（K03）

每格依次为A评分、B评分：

| A \ B | 甲 | 乙 |
| --- | --- | --- |
| 甲 | 活/1，活/1 | 死/0，死/0 |
| 乙 | 死/0，死/0 | 活/1，活/1 |

通过的是甲甲、乙乙，且两组评分相同。如果各人独立各半抽取，会有一半概率落入已经被排除的甲乙、乙甲。建议随机选完整组合，然后一起锁定各人的分支。

### C03：都无法单独改好，但一起换可以共同变好（K04）

| A \ B | 甲 | 乙 |
| --- | --- | --- |
| 甲 | 活/1，活/1 | 死/0，死/0 |
| 乙 | 死/0，死/0 | 活/2，活/2 |

甲甲、乙乙都通过已认可的筛选：任何人在甲甲中单独改选都会死亡。但乙乙使两个人都同样安全、多一次击杀，所以不是同分随机问题。

建议增加“共同改进”筛选，取乙乙。此建议需要用户确认；单凭已有的单人改选筛选不能自动得出它。

### C04：两个通过组合各对不同的人更有利（K05）

| A \ B | 甲 | 乙 |
| --- | --- | --- |
| 甲 | 活/2，活/1 | 死/0，死/0 |
| 乙 | 死/0，死/0 | 活/1，活/2 |

甲甲、乙乙都通过，A偏好甲甲，B偏好乙乙。两组的总击杀数还相同，所以把个人评分相加也无法解决，更不能据此认定它们对每个人都同效。

可能的玩法选择是把无法共同改善的冲突组合一起抽签，但这属于新的冲突裁决规则；现有“同效随机”没有自动授权它。这里暂不引入复杂的长期期望优化。

### C05：所有组合都有人想改，形成循环（K06）

| A \ B | 甲 | 乙 |
| --- | --- | --- |
| 甲 | 活/1，死/0 | 死/0，活/1 |
| 乙 | 死/0，活/1 | 活/1，死/0 |

一个完整循环：甲甲中B改乙保命 → 甲乙中A改乙保命 → 乙乙中B改甲保命 → 乙甲中A改甲保命 → 回到甲甲。四个组合都不能通过。

此时反复迭代不能靠多算几轮保证得到固定结果；停在第几轮会产生人为偏好。可能的兜底包括“在全部合法组合中抽取一次”或“本回合按特别规则抵消”，但二者都改变玩法，费用/资源/历史处理也不同，不能未经确认采用。若后续没有实际招式能够形成这种结构，不必为了抽象例子先做复杂实现。

### C07：某人局部同分的分支，可能不属于最终通过组合（K07）

| A \ B | 甲 | 乙 |
| --- | --- | --- |
| 甲 | 活/1，活/1 | 活/2，活/0 |
| 乙 | 活/1，活/0 | 活/0，活/1 |

只有甲甲通过。但固定B为甲时，A选甲或乙都是活/1；如果据此再对A随机，可能跳到乙甲，而B随即有改乙获益的机会，最终状态不再满足已认可的筛选条件。

建议把随机候选范围定义为**已经整体通过筛选的完整组合**。这意味着个人单独看同分的分支，不保证都能进入最终随机候选；此范围限制需用户明确，不能掩盖为实现细节。

### C08：组合等概率，不等于每个人各分支都各半（K11）

结构表中甲甲、甲乙、乙甲均为“活/1，活/1”，乙乙为“死/0，死/0”。前三组通过且同分，乙乙不通过。

若三个完整组合各以1/3概率抽取，对A和B分别来说，甲的概率都是2/3，乙都是1/3。不是实现偏向，而是候选组合构成的结果。

建议把“随机公平”具体定义为合法候选组合之间等概率；如果要求每个人的分支各半，就需另一种联合概率分配，而且可能必须让某些通过组合概率为0。当前尚未确定随机分布，不预设两种公平要求可以同时满足。

## 四、相邻边界：哪些已清楚，哪些还缺规则

| 编号 | 边界 | 当前结论/待定项 |
| --- | --- | --- |
| E01 | 一个候选活着，另一个死但击杀更多 | 已确认选能活的候选，不用杀伤抵偿死亡；K12检查给定评分表 |
| E02 | 所有候选都死 | 已确认继续比较击杀数，相同随机；K08/K09检查给定评分表 |
| E03 | 同一目标有多个有效击杀来源 | 已确认各来源独立计数，目标只淘汰一次 |
| E04 | 自己本轮会淘汰，但本轮攻击仍有效 | 已确认不能提前移除本人或删除已成立作用，击杀仍按有效作用统计 |
| E05 | 对手也在本轮淘汰，他的反弹是否保留 | 已确认保留，M02中反弹者淘汰后仍使Pragon使用者淘汰 |
| E06 | 自bi对至少一人成功 | 已确认全场成功防御先生成，所有逐对作用读取同一属性；改试另一个候选时重新生成全场属性 |
| E07 | 自bi没有成功对象 | 已确认自身必淘汰；不自动把这种自身淘汰算成任意其他人的击杀 |
| E08 | 普通攻击被吸收防住，但目标另被自bi淘汰 | 普通攻击不计击杀；自bi的有效击杀分别计数；吸收所得DD不进入分支优劣评价 |
| E09 | 同强攻击、普通削防御例外、专属防御 | 分别使用通则与明确例外；不能把“同效随机”变成普通攻防平手随机判胜 |
| E10 | 成功自bi与历强等直接淘汰相遇 | 全场无穷防御与特殊淘汰的优先关系仍待定；不能填成必活或必死后用作选择依据 |
| E11 | 反弹产生的击杀算谁 | 反弹者、原攻击者及自反伤的归因仍需具名案例；死亡结果已知不等于评分已知 |
| E12 | 全员最终淘汰 | 已有双方纯自bi都淘汰案例；整局结果名称及展示待定，不与双方历强本回合抵消混用 |
| E13 | 非法招式/候选，或资源不足 | 持有与合法性在选择前检查；非法提交如何处罚仍待定，不能把非法候选当“死/0”参加筛选 |
| E14 | 候选费用、免费来源与复制 | 候选试算不实际扣费；最终按声明招式/来源规则扣一次，不因取三雷就擅自改成普通三雷价格 |
| E15 | 回合历史记录与历强/张新伟 | 记录外层复合招还是选定分支、复制后的来源继承仍待核对；会影响当前/后续条件时须先解决 |
| E16 | 试算污染炸药队列、buff、次数 | 试算只读固定输入；每个组合互相隔离，最后只应用一次结果。旧代码已知列表副作用不能带入新选择逻辑 |
| E17 | 重复提交、断线恢复、重放 | 复用该回合已选组合和随机结果，不能重新抽签或重复扣费；具体联机协议后续实施包定义 |
| E18 | 玩家编号或遍历顺序改变 | 固定随机选择后，作用/评分/通过集合应只作对应的玩家重命名，不应改变谁占优势 |
| E19 | 反弹链、同回合特殊状态改变 | 超出已经明确的M02等案例部分待定；不能用现成双人结果拼接完整多人结果 |
| E20 | 单名吸收面对多个攻击的DD总收益 | 仍待确认叠加/上限；多人各吸收同一攻击则已明确各得全额。通常不进入有利评分，但不能据此省略正式资源结算 |

## 五、给程序的最小表达

沿用已有草案中的动作与作用记录，不新建通用规则语言。分析阶段只需：

1. `branch_options`：每名选择者有哪些合法分支。
2. `profile`：本次试算中每名选择者选哪个分支。
3. `result`：全场作用、存活/淘汰、费用与状态变化；从作用提取各人的`kill_targets`。
4. `scores`：各选择者的`(self_survives, kill_count)`。
5. `improvement_witness`：若排除某组合，记录谁换成哪个分支后，评分从什么变成什么。
6. `selected_profile`：最终选定的完整组合，以及选择/抽签依据；无需永久保存所有试算对象。

评分不完整时返回明确的未决规则原因；完整表没有通过组合时返回“无通过组合”；两者不得都用空列表表示。上述是分析结果分类，不是已经批准的线上错误处理或回合惩罚方案。

## 六、验证与旧程序边界

运行：`python3 experiments/r01-t01-a/check_branch_tables.py`。输出见`branch-case-checks.json`。13张评分表通过预期筛选断言，2张不完整/未知评分表被拒绝。抽象表为K03/K04/K05/K06/K07/K11；K01/K02/K10为注明依据的规则推导；K08/K09/K12为已确认的给定评分比较；K00为无选择者结构。

该脚本只检查事先给定的评分表，**没有实现或验证完整多人战斗**，不导入旧引擎、不加载AI、不进行随机选择、不修改资源。它给出每个被排除组合的改选依据，便于复查。

原代码`deidei_env.py`的`select_quantum_outcome`已有双人分支枚举与单方改选比较，但评分只按胜负记1/-1/0，多个通过组合取首个，无通过组合再按双方分数和取结果。它不能证明新人数评分、同效随机或多人规则已经实现。AI训练时的实际规则版本仍未知。

本轮另运行`python3 scripts/check.py`：语法检查11个Python文件；32项原测试中31通过，1个原有预期失败。该结果不是新规则验收。未修改游戏源码、模型、原有测试，也未提交。

## 建议的讨论顺序

先确定C07/C08的随机范围和分布，再决定C03是否排除能共同改进的组合。C04/C05先保留边界定义，并优先查是否存在依赖已明确招式的真实案例；未确定前不以玩家顺序或旧程序兜底补齐。
