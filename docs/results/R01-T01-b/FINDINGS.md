## F01 · P2 · 明确冲突：未写击杀集合默认为空，与多组案例的必要结果冲突

- 位置：[CASES 默认约定 L11](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/CASES.md#L11)、[C007 L73—75](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/CASES.md#L73)。默认约定写“未列出的击杀目标集合为空”。C007 只列 A 淘汰、B 获胜和充能，没有 B 的击杀目标。
- 最小例：按 C007 默认，A 普通防御，B Pragon，各 DD=10。Pragon 2 穿过普通防御 1，必须登记 `kills(B)={A}`；A 基础充能 1，B 支出 2，B 获胜。按默认空集合则得到 `kills(B)={}`，两者不能同时成立。获胜不能直接替代击杀：C027 的 B 因对方自 bi 失败获胜，正确击杀数就是 0。
- 依据：[R04 L49](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/RULEBOOK.md#L49)、R05、R06；[原答复第11—12轮 L207—212](https://github.com/Kalopsiazza/DeiDei/blob/d3a1e5842781fed433799c940619ab38da0230be/docs/results/R01-T01-a/ANSWERS.md#L207)明确分别归因；第23轮 L379、第24轮 L391 明确回击归属。
- 受影响：R04/R05/R11/R18；涉及多个 E 入口，最小例 E03/E12。20 组未明确写全作用者的击杀集合：C007、C009、C012 的 bi 子例、C015、C016、C024 的反弹子例、C030、C033、C035、C037、C048、C051、C052、C053、C062、C068、C070、C071、C074、C080。各应有的集合见 COVERAGE。部分可以从攻击动作推知，但这与“未列出即空”的严格默认冲突。已经在文字中明确写出“某人击杀／淘汰某人”的 C036、C043、C058 等不机械按缺少花括号报错。
- 建议：保留完整预期的目标，逐组补齐击杀集合；或者明确未写字段仅未断言，不能默认为空，并另补全量账目断言。不能用“最终赢家拥有所有击杀”补齐。
- 反向复核：补集合不改变已写胜负、支出或吸收收益；C027/C028 的空击杀必须保留。分支评分只数本人的不同有效目标，不数全场死亡数。

## F02 · P2 · 明确覆盖缺口：C066/C067 未设置曾义的上一实际招式

- 位置：[默认历史 L7—9](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/CASES.md#L7)、[C066/C067 L604—615](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/CASES.md#L604)。系统休整会覆盖 recovery 状态，但未覆盖“上一实际招式为空”。
- 最小反例是一个错误实现：仅比较本轮与上轮实际身份，完全漏掉休整豁免。在现有 C066，A 本轮 ZengYi、上一招空，因此错误实现也不会因 A 成功；在 C067，它也只找到重复 Bi 的 C。两例仍得到已写结果，无法识别被测缺陷。这是测试设计的反例，没有编写或运行该错误引擎。
- 应有输入与预期：C066 给 A `last_actual_move=ZengYi`、本轮系统休整；B 历强 DD=1，C bi 上一招 Charge。B 仍必须失败并被 C 击杀。C067 同样给 A 上一招 ZengYi；B 历强的合规目标严格只有 C，不能包含 A，即使错误追加的 10000 会被 A 无穷防住。
- 依据：[原第33轮 L549—562](https://github.com/Kalopsiazza/DeiDei/blob/d3a1e5842781fed433799c940619ab38da0230be/docs/results/R01-T01-a/ANSWERS.md#L549)、R15 L194/R25 L274，受影响 G19/G47、E26/E32、C066/C067。
- 建议：补上一招或从 T 发动连续推进到 T+1；同时断言条件成功与目标集合，不能只看 A 是否存活。两种补法均保留已确认胜负，没有新玩法。

## F03 · P2 · 待澄清：有延迟状态的合成输入缺少到期字段

- 位置：[默认 L7](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/CASES.md#L7)、C057 L523、C064 L586、C068 L622、C071 L649；[架构 A03 L34—37](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/architecture/RULE-ENGINE-v1.0.md#L34)、A05 L72、A09 L122—125。
- 最小例：C071 只写 A 曾义 waiting／已完成休整，没有当前局／回合与 `reward_due_turn`；默认又说无延迟项目。架构规定 waiting 有到期值，输入校验要核对延迟属于当前局。照字面填 null 会缺少应有字段；自行填“未来”或“本轮末”又会产生不同的奖励账目。B 的 bi 使 A 淘汰这一结论不受影响，但完整回合账目无法唯一写出。
- C068 waiting 子例同样缺少到期值：两种填法均可新局重置，但其中一种在重置前发奖、另一种不发奖。C064 的“待成熟1”未指定成熟时点，清空前是否有成熟记录也不同。C057 已说明“当轮末将成熟”，仍需统一当前局／回合的展开方式。
- 依据：原第33轮 L558 给 T+4 末时点；[原第38轮 L659—662](https://github.com/Kalopsiazza/DeiDei/blob/d3a1e5842781fed433799c940619ab38da0230be/docs/results/R01-T01-a/ANSWERS.md#L659)要求先记账后重开。受影响 R19/R25/R26、E10/E27/E32/E33、C057/C064/C068/C071。
- 建议：为这些合成例补明确局编号、回合与成熟／奖励到期值，并注明未断言的事件字段；或列一个统一且可复用的展开约定。到期恰逢淘汰／新局的分支单列，保留“账目先发生，新局再清除”。这里报告输入不足，不替规划者决定具体测试值，也不主张修改 T+4/T+5 规则。

## F04 · P2 · 明确覆盖缺口：C073 的输入不可能发曾义奖励

- 位置：[C073 L667—669](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/CASES.md#L667)，只复用 C017/C026/C060/C063。四组都沿用曾义 unused、无奖励到期的默认输入，却要求验证“不重发奖励”。
- 最小反例是一个只在曾义到期回合重试时重复发奖的实现；它在上述四组根本不会走发奖路径。因此这些输入不能证实该项要求。已有 C065 验证一次自然发奖，但没有重试到期回合。
- 应增加的验证：复用 C065 的 r5 到期状态，对同一 match/game/turn 重试，核对只有一份奖励和一份发奖记录；继续到 r6 使用后再次重试旧 r5，不得恢复已消费奖励。纯核心重复计算应输出相同账目；房间应用账目去重应另测，不能将两者混称。
- 依据：[架构 A04 L64—68](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/architecture/RULE-ENGINE-v1.0.md#L64)、A09 L125、A12 L150，R02/R25；原第33轮 L558/L562 的唯一奖励。涉及 E32/E33、C065/C073。
- 建议不改变 C065 的 r5/r6 时点或奖励数量，只补非空发奖路径的重试验收。规则本身已有要求，无需重新讨论玩法。

## F05 · P3 · 明确遗漏：G59 的“攒防御0”未落入所指正文

- 位置：[TRACEABILITY G59 L84](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/TRACEABILITY.md#L84)指向 R05/R08。R05 解释 0 攻击和直接淘汰，R08 列防御表却无攒；[E01 L107](https://github.com/Kalopsiazza/DeiDei/blob/3a81daf0f42416ccb73a5a69748655145e6f2f0c/docs/rules/v1/RULEBOOK.md#L107)也只写攻击0。全文未明确给出攒的防御数0。
