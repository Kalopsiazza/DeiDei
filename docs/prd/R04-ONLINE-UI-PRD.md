# R04 好友房 UI 重构 PRD 与逐镜分镜

2026-10-02 返工：本文件的业务与页面关系保留；独立中庭素材及每页重新缩放的落地方案被 [连续镜头与共享 UI PRD](R04-ONLINE-CONTINUITY-PRD.md) 替代，以该文件为视觉实施准则。

- 编号：UI-R04-ONLINE
- 版本：1.0（2026-10-01 已通过）
- 日期：2026-10-01
- 适用范围：`work/r04-t01-b-frontend-live` 的桌面 Electron 前端
- 正式名称：截图一及其默认状态统一称为「联机前厅」

## 1. 问题

现有好友房入口、创建／加入表单和大厅虽然已经能连接 `rooms-1.1`，但仍沿用通用顶栏、居中矩形面板、普通表单和旧联机牌桌。它与主菜单、单人准备、镜头推进、薄毛玻璃及正式战局的视觉语言不连续，创建成功后还会进入 `OnlineRoom` 内部的旧 `.online-table`，没有使用已经完成的 2—6 人战局舞台。

本轮需要把好友房改造成一条连续空间路径：主菜单进入联机前厅，在同一场景的左右两侧完成创建或加入，成功后继续深入房间大厅，再经多人入场进入正式战局。界面必须清楚表达连接、角色、准备、房主和错误状态，同时不能用动效掩盖等待或伪造服务端能力。

## 2. 目标

1. 玩家进入后第一眼只看到两条主路径：创建房间、加入房间。
2. 主菜单、联机前厅、创建／加入、房间大厅、多人入场和正式战局使用连续镜头关系。
3. 创建和加入不再表现为网页卡片或后台表单，而是同一通讯中庭中的左右操作区。
4. 房间大厅以参战席位为主，观众区独立，房主与准备状态明确。
5. 正式多人对局复用既有正式战局舞台、卡面、操作区和 2—6 人席位系统；在线层只提供状态与命令。
6. 模拟服务始终标记 `MOCK`；真实联网验收与前端演示严格区分。
7. 键盘、焦点、减少动态和 1000×650 至 1920×1080 的窗口仍可使用。

## 3. 非目标

- 不新增公开房间列表、匹配、账号、好友系统、聊天、排行或成长。
- 不新增房间名称、可选参战人数上限或多人 AI。
- 不改变房间号格式、密码校验、规则版本、超时、掉线、缺席或房主离房策略。
- 不在 renderer 复制规则计算，不提前获得或隐藏其他玩家未公开招式。
- 不新增动画库、组件库或网络协议。
- 不将 scripted fake socket 当作真实联网验收。

## 4. 页面关系与命名

```text
P02 主菜单
  └─ L01 联机前厅
       ├─ L02 房间部署（创建房间）
       └─ L03 房间接入（加入房间）
              └─ L04 房间大厅
                    └─ L05 多人入场
                          └─ L06 正式战局
                                └─ L07 联机结算
                                      ├─ 返回 L04 准备下一局
                                      └─ 返回 P02 主菜单
```

L01、L02、L03 共用「通讯中庭」主场景；L02 使用中庭左侧扩图，L03 使用右侧扩图。L04 位于中庭更深处。L05 以门体、前景遮挡和毛玻璃连接 L04 与现有正式战局背景。L06 不再使用旧 `.online-table`。

## 5. 视觉与素材关系

### 5.1 连续空间

- 主菜单：建筑外部或人物所在的主视觉层。
- 联机前厅：镜头进入建筑内部后的通讯中庭。
- 房间部署：中庭左侧房主控制台，暗红信号向外扩散。
- 房间接入：中庭右侧接入终端，冰青信号向远处收束。
- 房间大厅：中庭后方更深的席位空间。
- 正式战局：复用现有战局背景，通过门体和毛玻璃完成镜头交接。

素材应共享消失点、黑色金属／玻璃材质、冰青与暗红光源。优先制作一张中庭主背景和左右／后方扩图，不为每页生成互不相关的独立场景。图中不生成文字，所有文字与状态由前端绘制。

### 5.2 共同界面原则

- 不显示通用顶栏，不在页面中央放大矩形容器。
- 主动作固定右下；返回动作固定左上并复用现有返回组件。
- 标题、表单和错误信息分别占据不同景深层，不用大色块铺底。
- 创建使用暖红发射信号，加入使用冰青接入信号；颜色只区分路径，不表达危险等级。
- 连接状态为角落里的信号点与短文字；开发 `MOCK` 标记固定左下且不抢主视觉。
- hover、focus、active 不覆盖文字，文字对比度在任何状态下保持可读。

## 6. 页面需求

### 6.1 L01 联机前厅

标题使用「叫上朋友，一起出招。」。创建和加入是嵌入场景的两组空间入口，不画成两张玻璃卡片。

- 创建房间：位于左侧偏下，暖红信号环向外展开，说明「发起一个好友房」。
- 加入房间：位于右侧偏下，冰青扫描线向内收束，说明「输入房间号接入」。
- 本机档案仅以小头像＋昵称放在次要角落，不形成身份横栏。
- 已连接、连接中、重连中、服务不可用均保持同一布局；未连接时两条主路径禁用并显示就地重连动作。
- 进入页面后默认焦点落在创建房间；左右方向键可在两条路径间移动。

### 6.2 L02 房间部署

镜头从 L01 向左前方推进，背景的房主控制台进入清晰区。配置沿一条纵向导轨排列，不使用普通下拉表单。

1. 规则：只读「经典规则 1.0.1」。
2. 参战席位：只读「2—6 位真人」，不提供当前协议没有的容量设置。
3. 每拍时间：从服务端 `allowed_turn_ms` 动态生成横向刻度选择器。
4. 提前揭晓：机械拨片式开关，对应 `early_reveal`。
5. 观众容量：从 0 到服务端 `spectator_max` 的步进刻度。
6. 房间密码：默认锁闭；启用后展开现有密码输入，不改变长度和校验规则。

主动作「创建房间」固定右下。提交期间所有配置锁定，控制台出现沿导轨移动的扫描光；失败后保持用户已填内容。创建成功后不硬切，前方门体开启并进入 L04。

### 6.3 L03 房间接入

镜头从 L01 向右前方推进。房间号是第一视觉焦点，使用大字号、宽字距的单一输入，不根据示例房号假设固定长度。

- 房间号：自动显示为大写视觉样式，但继续使用既有输入和服务端校验。
- 身份：参战／观战表现为两张前后轮换的身份凭证；切换只改变提交的 `role`。
- 房间密码：始终作为可选次级输入，避免前端预查询房间是否有密码。
- 主动作「接入房间」固定右下。
- `ROOM_FULL` 或 `MATCH_IN_PROGRESS` 时，在原位置出现「以观众身份接入」，不弹出第二个页面。
- `ROOM_ACCESS_DENIED` 统一显示「房间号或密码不正确」，不泄露房间是否存在。

接入成功后经同一门体进入 L04；返回时镜头沿原路径退回 L01，不丢失尚未提交的内容，离开联机前厅时才清空。

### 6.4 L04 房间大厅

大厅以参战席位为主，不延续旧的六张矩形列表。

- 六个参战位置组成面向中央房间信标的空间阵列；空位只保留席位编号与低亮轮廓。
- 中央信标显示房间号和复制动作；密码仅显示「已设置」，不显示内容。
- 每个玩家只显示头像、昵称、房主／本人标识、在线和准备状态。
- 观众位是独立窄区，不占六个参战位置。
- 普通玩家右下显示准备／取消准备；房主右下显示开始对局。
- 开始条件在主动作附近使用一句可操作原因：至少两位玩家、有人掉线、有人未准备。
- 角色切换保留现有服务能力；房主不得转为观众。
- 房主离开、普通玩家离开和断线恢复继续使用共享科技弹窗或就地状态，不改变服务语义。

### 6.5 L05 多人入场

房主开始后，六个席位向中央信标收束，镜头穿过大厅后方入口。玩家按服务端 `roster_profiles` 与 seat 顺序进入；本机使用冰青描边突出，不生成统一身份长条。

- 2 人时使用更大的头像、名字和更紧凑的对阵距离。
- 3—6 人时按正式战局已有席位几何进入。
- 入场只展示身份与本局规则，不展示未公开招式。
- 动画结束后才挂入选卡操作区，禁止首帧闪现手牌。
- 减少动态模式跳过连续推进，只保留席位确认和短淡入。

### 6.6 L06 正式战局

正式多人对局复用既有 `.battle-table` 的舞台、卡面、操作区、资源、历史牌、暂停／局势弹窗及 2—6 人席位设计。需要新增的是在线状态适配，不是第二套视觉组件。

- 在线 snapshot 是唯一显示来源；提交继续调用 `online.submit`。
- 选择阶段只显示本人有权看到的 options；已提交后锁定，不允许改牌。
- 揭晓阶段读取公开 `last_turn`；多人真实保留服务端 `reveal_ms`，当前默认 5 秒。
- 暂停菜单不能暂停服务端牌局；冻结禁用；房间设置仅展示或调用服务端已有能力。
- 观众和已淘汰玩家不显示选卡操作区，也不能提前看到未揭晓动作。
- 掉线和重连不切换到另一套页面，保留当前公开战局并显示恢复状态。

### 6.7 L07 联机结算

复用正式整场结算视觉并适配 2—6 人。结算只展示公开结果、最后一拍与玩家状态；本机保持冰青强调。

- 房主显示「准备下一局」，调用现有 `returnLobby` 后返回 L04。
- 其他成员显示「等待房主开启下一局」。
- 可打开局势回顾；多人左栏显示本局淘汰记录。
- 返回主菜单或退出房间都先完成结算退场和毛玻璃交接，不硬切。

## 7. 状态与数据约束

| UI 内容 | 当前来源 | 规则 |
| --- | --- | --- |
| 连接状态 | `OnlineState.status` | idle／connecting／connected／reconnecting／unavailable 原样表达 |
| 开发演示 | `OnlineState.source` | fixture 时必须显示 `MOCK` |
| 每拍时间 | `hello.capabilities.allowed_turn_ms` | 不在前端写死新增档位 |
| 参战人数 | `hello.capabilities.max_players` | 只读说明，不增加创建参数 |
| 观众容量 | `hello.capabilities.spectator_max` | 创建时允许 0 至上限 |
| 创建设置 | `turn_ms`、`early_reveal`、`spectator_cap`、可选密码 | 不添加房名或人数上限 |
| 加入设置 | `room_code`、可选密码、player／spectator | 不预查询房间私密信息 |
| 大厅成员 | `snapshot.view.members` | 参战与观众分区，席位按 seat |
| 开始条件 | 现有 `startReason` | 至少两人、全员在线并准备 |
| 对局信息 | `snapshot.view.match` | 不从 UI 推导隐藏状态 |
| 揭晓与结果 | `last_turn`、`effective_outcome` | 只显示服务端已公开内容 |

## 9. 动效规则

- 主要页面转场只动画 `transform`、`opacity` 和背景毛玻璃强度。
- 同一层同一时刻只有一个 transform 动画拥有者；背景、内容和席位分层。
- 不用整页旋转、持续抖动、强白闪或遮挡文字的扫光。
- 等待请求时场景保持稳定，循环只发生在局部信号／扫描层。
- 请求超过视觉预期时继续显示真实连接状态，不用假进度条走到 99%。
- `prefers-reduced-motion` 下：取消连续镜头缩放与横移，以 120—180ms 淡入淡出、静态方向标记和明确标题替代。

## 10. 错误与恢复

- 服务未配置／不可用：停留 L01，创建和加入禁用，提供重连；单人入口不受影响。
- 重连中：保留所在页面与已公开内容，阻止会冲突的新命令。
- 房间号或密码错误：停留 L03，保留输入，不区分具体原因。
- 参战位满／比赛已开始：停留 L03，明确提供观战入口。
- 观众位满或关闭：停留 L03，不提供无效观战动作。
- 房主离开或房间结束：说明原因后退回 L01，不关闭应用。
- 会话被替换、服务重启或临时身份过期：清除旧房间状态，回到 L01 重新连接。
- 创建／加入按钮在 pending 状态锁定，避免重复提交。

## 11. 可访问性与窗口适配

- 所有空间入口、刻度、拨片、身份凭证和席位仍使用语义化 button／input／fieldset。
- 键盘可完成进入、配置、创建、加入、准备、开始、离开和错误恢复。
- 焦点样式使用前景描边与光晕，不依赖背景色变化。
- 错误与连接变化使用 `role=status`／`role=alert`，不重复朗读装饰文字。
- 1000×650 不裁掉主动作或房间号；必要时压缩场景留白，不缩小正文到难读尺寸。
- 1366×768 是主要桌面验收尺寸；1920×1080 检查空间比例和过度拉伸。

## 12. 实现边界

- 保留现有 `NetworkRoomPort`、preload 白名单和在线 API；本轮不改协议。
- `OnlineRoom` 继续拥有联机状态和命令，但入口／大厅与正式战局视图需要拆清，避免单个组件继续同时承担所有阶段。
- 正式战局使用现有战局舞台组件和交互规则；如果当前仍内联在 renderer，实施计划只提取完成在线复用所需的最小共享边界，不做无关架构重写。
- 规则名称、招式图标、卡面、局势弹窗和共享 Modal 使用现有资产和标准。
- 背景资产生成须在 PRD 审阅后单独进行，先出通讯中庭主图，再扩左／右／后景；不生成文字或品牌标识。

## 13. 验收标准

- AC-01：以后提到「联机前厅」能唯一对应 L01，不再使用模糊的“截图一”。
- AC-02：主菜单到 L01、L01 到 L02／L03、成功到 L04 均有连续镜头关系，无硬切。
- AC-03：L01 无通用顶栏、居中大矩形或普通双按钮排版。
- AC-04：创建只提交当前协议支持的密码、时间、提前揭晓和观众容量。
- AC-05：加入支持参战／观战、可选密码及满员后的显式观战降级。
- AC-06：大厅正确区分六个参战席位与独立观众区；至少两人、全员在线准备后房主才能开始。
- AC-07：多人开局进入正式战局舞台，不渲染旧 `.online-table`。
- AC-08：正式战局不泄露未揭晓招式；提交锁定、观战、淘汰、重连和 5 秒揭晓保持原服务语义。
- AC-09：房主下一局返回 L04，所有参战者重新准备；普通成员等待房主。
- AC-10：MOCK 始终可辨，且文档与验收不把它称为真实联网。
- AC-11：1000×650、1366×768、1920×1080 无主动作裁切、横向溢出或关键文字重叠。
- AC-12：减少动态模式能完成全部流程，且不依赖大幅镜头运动理解状态。

## 14. 验证计划

1. 静态：类型检查、构建、`git diff --check`。
2. 联机模型：现有 `test:online` 全部通过，确认协议和隐私边界未变。
3. Mock Electron：创建、加入错误、满员转观战、六席大厅、准备、开始、提交、揭晓、结算、下一局和离房。
4. 正式 main：无服务时明确不可用；配置服务时不注入 scripted fixture。
5. 视觉：三个目标尺寸逐状态截图，检查联机前厅、两条支线、大厅、2 人／6 人入场与战局、胜利／无人存活结算。
6. 动效：记录主菜单→前厅→大厅→正式战局以及结算→大厅；检查首帧闪现、背景差异、重复 transform、退出抽搐与减少动态。
7. 安全：确认 renderer 状态没有 resume token、密码回显、其他玩家未公开招式或可注入 URL。
